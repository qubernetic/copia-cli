## [Unreleased]

### Added

- `auth setup-git [--host <host>] [--force/-f]` makes copia-cli the git credential helper, as in `gh`: for every logged-in host, or the one `--host` names, it runs `git config --global --replace-all credential.https://<host>.helper ""` (dropping the helpers configured before) and then `--add` of `!'<path of copia-cli>' auth git-credential`, so `git clone`, `fetch` and `push` over https use the stored token. The path is the `copia-cli` in `PATH` when that is a symlink to the running binary, otherwise the running binary, always single-quoted. A re-run changes nothing. A host that is not logged in fails unless `--force`, which needs `--host`; no host logged in fails. `COPIA_HOST` does not narrow it. It reads no token and makes no API call (#423)
- `auth git-credential <get|store|erase>`, a hidden command git runs as a credential helper, as in `gh`. For `get` with `protocol=https` and a configured host it prints `username=<login>` and `password=<token>` of the host's active account, the token read from the config file or the OS keyring; the host matches regardless of case and its port must match (a missing port is 443), and a path in the request is ignored. A `url` line is read too, and a `username` in the request must be the active account's login. Anything else (`http`, an unknown host, another port) prints nothing and exits 0; `store` and `erase` do nothing. `--token`, `COPIA_TOKEN` and `COPIA_HOST` do not apply, since git asks for each host separately. A token or login with a character outside printable ASCII (a line break included) is refused with an error that names the host, never the token. The host matching of `repo clone` moved to `pkg/cmdutil`, shared by both commands (#422)
- `auth switch [--host <host>] [--user/-u <login>]` changes the active account of a host and makes that host the default host (`default_host`), as in `gh`, and prints `Switched active account for <host> to <login>`. `--host` alone switches to the host's only account, or with two accounts to the one that is not active. Without flags it switches to the other account when exactly two accounts exist in total, on one host or on two. In every other case it fails and lists the accounts to choose from, one `<host> <login>` per line; there is no prompt. An unknown host or login fails without writing the config file. The tokens stay where they are stored, so the keyring is not touched; when `COPIA_TOKEN` is set, a warning says that it applies only with `COPIA_HOST` (or `--host`) and that the commands otherwise use the token of the active account. A host entry of the old shape whose token has no login cannot be switched on (`run auth login`), so that token is never bound to another account. No API call (#421)
- `status` prints gh's dashboard across repositories: `Assigned Issues` and `Assigned Pull Requests` side by side, then `Review Requests` and `Mentions`, then `Repository Activity`, each section with `Nothing here ^_^` when empty. A row shows `owner/repo#<number>` and the title, cut to the width of its column; the half-width sections show the five most recently updated open issues or pull requests and Repository Activity your ten most recent notifications, read or unread, with `issue`, `PR`, `commit` or `repository`. The layout follows the terminal width, 80 columns when the output is not a terminal, and the output goes through the pager. The first four sections come from `GET /repos/issues/search` with `state=open` and `assigned=true` (split into issues and pull requests), `review_requested=true` with `type=pulls`, and `mentioned=true`, 25 results each as in gh; the activity from `GET /notifications?all=true`. `--org/-o <owner>` limits every section to the repositories of one user or organization (the search's `owner` parameter, an unknown one fails with `no user or organization named`), and `--exclude/-e owner/repo` (comma-separated or repeated) drops repositories, matched regardless of case. Unlike gh, the activity is your notifications, since Copia has no event feed (#44)
- `pr status` shows the pull requests of the current repository (or `-R owner/repo`) that are relevant to you, as in `gh`: `Current branch`, `Created by you` and `Requesting a code review from you`. A row shows `#<number>`, the title (cut to 50 characters) and `[<head branch>]`, a closed or merged pull request adds ` - Closed` or ` - Merged`, and `--conflict-status/-c` adds `✓ No merge conflicts` or `× Merge conflicts` to an open one. Each section shows the ten most recently updated pull requests and `And N more`; an empty one prints `There is no pull request associated with [<branch>]` (or `There is no current branch`), `You have no open pull requests` or `You have no pull requests to review`. With `-R` the current branch section is left out, as in gh. The current branch and your pull requests come from `GET /repos/{owner}/{repo}/pulls` (when the branch has no open one, the 50 most recently updated closed ones are searched; a closed one of the default branch is left out), the review requests from `GET /repos/issues/search` with `type=pulls` and `review_requested=true`, matched to the repository on the client. There is no check or review summary line. `--json` prints one object with gh's keys `currentBranch` (or `null`), `createdBy` and `needsReview`, with the fields `number`, `title`, `state` (`merged` for a merged one), `html_url`, `user`, `head`, `base`, `updated_at`, `mergeable` and `draft`, and `--jq` and `--template`; the output goes through the pager (#404)
- `issue status` shows the open issues of the current repository (or `-R owner/repo`) that are relevant to you, as in `gh`: `Issues assigned to you`, `Issues mentioning you` and `Issues opened by you`, each with the ten most recently updated issues and `And N more` when there are more; an empty section prints `There are no issues assigned to you` (`mentioning you`, `opened by you`). On a terminal a row shows `#<number>`, the title, the labels and the update time in words, otherwise the number, the state, the title, the labels and the raw time. The sections come from `GET /repos/{owner}/{repo}/issues` with `assigned_by`, `mentioned_by` and `created_by` for the user of one `GET /user`; app.copia.io ignores `created_by`, so the author (and the assignees) are checked on each issue. `--json` prints one object with gh's keys `assigned`, `mentioned` and `createdBy`, each a list with the requested fields (`number`, `title`, `state`, `labels`, `updated_at`, `html_url`, `user`, `assignees`), with `--jq` and `--template`; the output goes through the pager (#403)
- `repo set-default [<owner/repo> | <remote>]` sets the default repository of the local git repository, as in `gh`: it marks the git remote that points to it with the git config key `remote.<name>.copia-resolved` (gh uses `gh-resolved`) and prints `Set <owner/repo> as the default repository for the current directory`. The commands that work on the current repository now read the marked remote first, then `origin`; `-R` still wins over both. `--view/-v` prints the default (or a note on standard error when none is set) and `--unset/-u` removes the mark from every remote, also from one whose URL names no repository. Remotes of a partial clone (`git clone --filter`) count like any other. The argument is `owner/repo` (any case) or a remote name, and must be one of the git remotes. There is no prompt: without an argument the only remote is used, and with several remotes the command fails and lists them. Outside a git repository the command fails with `must be run from inside a git repository`. No API call (#402)
- `browse` takes gh's targets: a commit SHA opens that commit, and a path opens the file or directory on the default branch (`/src/branch/<branch>/<path>`); `<path>:<line>` and `<path>:<start>-<end>` open the source view at that line or range. A relative path is taken from the current directory inside the repository, a path starting with `/`, or any path with `-R`, from the repository root. `--branch/-b <name>` and `--commit/-c=<sha>` choose the branch or commit (also without a path); `--commit` without a SHA opens the last commit of the current branch, or of the default branch with `-R`. `--blame` opens the blame view of the path. `--settings/-s`, `--wiki/-w`, `--releases/-r`, `--actions/-a` and `--projects/-p` open those repository pages. A number still opens the issue or pull request, and `--no-browser/-n` still prints the URL. Conflicting flags fail before anything opens, with gh's messages: an argument with one of the page flags, more than one of `--branch`, `--commit` and the page flags, `--blame` without a path, a number or SHA with `--branch` or `--commit`, and a malformed line. A path without `--branch` or `--commit` reads the default branch with `GET /repos/{owner}/{repo}`, and `--commit` without a SHA reads the branch with `GET /repos/{owner}/{repo}/branches/{branch}`, so these two need a token; everything else makes no API call (#401)
- `--web/-w` on `repo view`, `label list`, `search issues`, `search prs` and `search repos` opens the page in the browser instead, as in `gh`; no API call is made, so no token is needed. The browser and the `Opening <url> in your browser.` line on standard error work as for the issue commands. `repo view` opens the repository page and `label list` the labels page. `search issues` opens the issue list of the repository with the query and `--state` (all states by default). `search repos` opens the explore page with the query, `--sort` and `--order`. Copia has no web search across repositories, so `search prs` opens the pull request dashboard (or the one of the `--owner` organization) with the query, `--state`, `--author` and `--assignee`, and with `-R` the pull request list of that repository. `--label`, and `--assignee <login>` with `-R`, print `warning: --<flag> is not applied in the browser` (#400)
- `--web/-w` on `pr view`, `pr comment`, `pr diff`, `pr list` and `pr create` opens the page in the browser instead, as in `gh`; no API call is made, so no token is needed. The browser and the `Opening <url> in your browser.` line on standard error work as for the issue commands. `view` and `comment` open the pull request page (`comment` also takes a pull request URL, and `--web` fails with `--body`, `--body-file` or `--editor`), `diff` opens its files tab. `list` opens the pull request list with `--state`; the web list has no merged filter, so `--state merged` opens the closed list with a warning. `create` opens the compare page `{base}...{head}` with the new pull request form expanded and `--title` and `--body` (or the `--fill` values) filled in; the head branch defaults to the current branch. `--label`, `--assignee` and `--milestone` print `warning: --<flag> is not applied in the browser`, and `--draft`, `--reviewer` and `--editor` fail with `--web`, as in `gh` (#399)
- `--web/-w` on `issue view`, `issue comment`, `issue list` and `issue create` opens the page in the browser instead, as in `gh`; no API call is made, so no token is needed. The browser is chosen like for `browse` (`COPIA_BROWSER`, then the config key `browser`, then `BROWSER`, then the system opener), and on a terminal `Opening <url> in your browser.` goes to standard error. `view` and `comment` open the issue page (`comment --web` fails with `--body` or `--editor`). `list` opens the issue list with `--state`, `--search`, `--author <login>`, and `--assignee @me` or `--author @me` as the web filters; `--label`, `--milestone`, `--mention` and `--assignee <login>` print `warning: --<flag> is not applied in the browser`, since the web list takes them only by ID. `create` opens the new-issue form with `--title` and `--body` filled in; `--label`, `--assignee` and `--milestone` print the same warning, and `--web` with `--editor` fails (#398)
- `alias set <name> <expansion>`, `alias list`, `alias delete {<name> | --all}` and `alias import [<file> | -]` manage command shortcuts, as in `gh`, stored under the top-level key `aliases` of `~/.config/copia/config.yml` beside `hosts` (mode `600`, `hosts` and the tokens are kept as they are). `copia-cli <alias> [args]` runs the expansion: `$1`, `$2` and so on take the arguments after the alias, otherwise the arguments are appended, and too few arguments for the placeholders fail with `not enough arguments for alias`. The expansion is split into words like a shell does before the placeholders are filled, so an argument stays one word and cannot add flags. An expansion that starts with `!`, or one set with `--shell/-s`, runs through `sh -c` with the arguments as `$1`, `$2` (never pasted into the script), and its exit status becomes the one of copia-cli. `set` refuses a name of a copia-cli command (also `help` and `alias`), a name that is empty, starts with `-` or contains blanks, an expansion that does not start with a copia-cli command (unless it is a shell alias) and an existing name without `--clobber`; `-` as the expansion reads it from standard input. A copia-cli command also wins over an alias of the same name written into the config file by hand. `list` prints the aliases as a YAML map sorted by name, the format `import` reads; `import` checks every alias like `set`, imports the valid ones, reports each refused one on standard error and then fails. No API call (#42)
- `--editor/-e` on `issue create`, `pr create`, `issue comment` and `pr comment` opens the editor on a temporary file and uses the saved text, as in `gh`. For the create commands the file holds the title on the first line and the body after a blank line, prefilled with `--title` (and for `pr create` the `--fill` values); the first non-blank line becomes the title and the rest the body. For the comment commands the file starts empty and the saved text becomes the body. The editor is chosen from `COPIA_EDITOR`, then the config key `editor`, then `VISUAL`, then `EDITOR`; with none set the command fails with a hint naming them. The command is split into words like a shell does (quotes and backslashes, no expansion) and run without a shell. Empty text aborts with `aborted: the editor text is empty` and no request, `--editor` with `--body` or `--body-file` fails before anything runs, and the temporary file (`copia-*.md`, mode `600`) is removed afterwards, also when the editor fails. There are no interactive prompts: the editor opens only on `--editor` (#397)
- The `pager` setting now takes effect: `repo list`, `repo view`, `issue list`, `issue view`, `pr list`, `pr view`, `pr diff`, `label list`, `release list`, `org list`, `org view` and `notification list` send their output through the pager when standard output is a terminal, as in `gh`. The pager is chosen from `COPIA_PAGER`, then the config key `pager`, then `PAGER`; none is the default, and `COPIA_PAGER=` (set but empty) or `cat` turns it off. The command is split into words at whitespace and run without a shell, with `LESS=FRX` and `LV=-c` unless they are set. Quitting the pager before the end is not an error, and a pager that cannot be started prints `failed to start pager: ...` to standard error and the output is printed without it. No API call (#396)
- The `output` setting now takes effect: with `output: json` in the config, or `COPIA_OUTPUT=json`, every command that takes `--json` prints all its fields as JSON when `--json` is not given, and `--jq` and `--template` work without `--json`. `COPIA_OUTPUT` beats the config key, and `COPIA_OUTPUT=table` or an explicit `--json` field list overrides the setting for one call; another value of either fails before any request with `invalid COPIA_OUTPUT "yaml": valid values are table, json` (or `invalid config key output ...`). There is no YAML output. `issue view` and `pr view` with `--comments` keep their text output under a configured `json`; with an explicit `--json`, `--jq` or `--template` they still fail (#46)
- `config list`, `config get <key>` and `config set <key> <value>` show and change the settings of copia-cli, stored as top-level keys of `~/.config/copia/config.yml` beside `hosts`. The keys are `output` (`table` or `json`, default `table`), `browser`, `pager` and `editor`. `config list` prints every key as `key=value`, `config get` prints one value (the default when the key is not set, nothing when it has none), and `config set` validates before it saves: an unknown key or a value the key does not allow fails without writing the file. `hosts` and the tokens are kept as they are, and every save of the file (also `auth login` and `auth logout`) now keeps the keys copia-cli does not know, at the top level and under a host, where it dropped them before. `browse` now reads the `browser` key, so the browser is chosen from `COPIA_BROWSER`, then `browser`, then `BROWSER`, then the system opener. No API call (#395)
- `search prs [<query>]` searches pull requests across every repository the token can read with `GET /repos/issues/search?type=pulls`, newest first and in every state unless `--state/-s {open|closed}` is given; an unknown state fails before any request. `--label/-l` (repeatable or comma separated, matches any of the names), `--author` (a login sent as `created_by`, `@me` as `created=true` with one `GET /user`; the author is also checked on each result, since app.copia.io ignores `created_by`), `--assignee` (`assigned=true`: the endpoint filters only on the authenticated user, so it takes `@me` or the user's own login, read with the same `GET /user`; another login fails), `--owner` (a user or organization) and `--limit/-L` (default 30, paged) are sent to the server. `-R owner/repo` sends the owner and keeps only the pull requests of that repository, since the endpoint has no repository filter; `-R` with another `--owner` fails. A merged pull request shows the state `merged`. The table prints the repository, number, title and state; `--json` takes `number`, `title`, `state`, `html_url`, `repository`, `user`, `labels`, `created_at` and `updated_at`, with `--jq` and `--template`. Without a query or a flag the command fails, as in `gh`; an unknown `--owner`, and on Gitea 1.26 an unknown `--author`, names the user that was not found (#376)
- `pr update-branch <number|url>` updates the branch of a pull request with its base branch through `POST /repos/{owner}/{repo}/pulls/{index}/update`: by default the base branch is merged into the head branch (`style=merge`), and `--rebase` rebases the head branch onto it (`style=rebase`). The pull request is read first: a closed or merged one fails, and when its `merge_base` is the tip of the base branch (`base.sha`) the note `! The branch of pull request <owner>/<repo>#<n> (<title>) is already up to date` goes to standard error and nothing is sent, as in `gh`. Success prints `Updated the branch of pull request <owner>/<repo>#<n> (<title>)`; a refused update (HTTP 409 for a merge or rebase conflict, 422) shows the server's message. The argument is a number, `#<n>` or a pull request URL; a URL on another host than the active one fails before any request (#375)
- `pr ready <number|url>` marks a draft pull request as ready for review. Gitea has no draft field, so the command removes the work-in-progress title prefix (`WIP:` or `[WIP]`, any case, with the spaces after it) with `PATCH /repos/{owner}/{repo}/pulls/{index}`; `--undo` converts the pull request back to a draft by prefixing the title with `WIP: `. The pull request is read first: one that is already in the wanted state gets the note `! Pull request <owner>/<repo>#<n> (<title>) is already "ready for review"` (`is already "in draft"`) on standard error and nothing is sent, and a closed one fails, as in `gh`. Success prints `Pull request <owner>/<repo>#<n> (<title>) is marked as "ready for review"` (`is converted to "draft"`) with the new title; a title that is only the prefix fails before any change. `pr create --draft` uses the same prefix check. The argument is a number, `#<n>` or a pull request URL; a URL on another host than the active one fails before any request (#374)
- `pr edit <number|url>` changes a pull request with `PATCH /repos/{owner}/{repo}/pulls/{index}`: `--title/-t`, `--body/-b` (an empty body clears it), `--body-file/-F` (`-` reads standard input), `--base/-B`, `--milestone/-m` (name or numeric ID), `--add-label`/`--remove-label` (repository and organization labels by name) and `--add-assignee`/`--remove-assignee` (`@me` is the authenticated user). Gitea's PATCH replaces the whole label and assignee lists, so the pull request is read first and the changed lists are sent; removing a value the pull request does not have changes nothing. `--remove-milestone` sends `milestone: 0` to the issue PATCH of the same index, since the pull request PATCH ignores it. `--add-reviewer`/`--remove-reviewer` take a login or an `org/team` name and use `POST` and `DELETE /pulls/{index}/requested_reviewers`. No flag, `--body` with `--body-file`, `--milestone` with `--remove-milestone`, a blank `--title`, the same value in an `--add-*` and its `--remove-*` flag, and an unknown label or milestone all fail before the pull request is changed. Success prints the URL of the pull request, as in `gh`. `pr view` now prints a `Labels:` line and takes `labels` in `--json` (#373)
- `pr comment <number|url>` adds a comment to a pull request with `POST /repos/{owner}/{repo}/issues/{index}/comments`. The body comes from `--body/-b` or `--body-file/-F` (`-` reads standard input); one of them is required, the two cannot be combined, and without either, or with a blank body, the command fails before any request. Success prints the URL of the new comment, as in `gh`. HTTP 404 reports the pull request as not found, and a refused comment shows the server's message. The argument is a number, `#<n>` or a pull request URL; a URL on another host than the active one fails before any request (#372)
- `pr reopen <number|url>` reopens a closed pull request with `PATCH /repos/{owner}/{repo}/pulls/{index}` (`state: open`). The pull request is read first: one that is already open gets the note `! Pull request <owner>/<repo>#<n> (<title>) is already open` on standard error and nothing is sent, and a merged one fails with `can't be reopened because it was already merged`, as in `gh`. `--comment/-c` posts a comment before the reopen. Success prints `Reopened pull request <owner>/<repo>#<n> (<title>)`; HTTP 404 reports the pull request as not found, and a refused reopen shows the server's message. The argument is a number, `#<n>` or a pull request URL; a URL on another host than the active one fails before any request (#371)
- `issue lock <number|url>` and `issue unlock <number|url>` lock and unlock the conversation of an issue with `PUT` and `DELETE /repos/{owner}/{repo}/issues/{index}/lock`. `--reason/-r` takes gh's values `off_topic`, `resolved`, `spam` and `too_heated` and sends them as Gitea's default lock reasons (`Off-topic`, `Resolved`, `Spam`, `Too heated`); an unknown value fails before any request. The issue is read first: `lock` fails on an issue that is already locked (Gitea cannot change the reason of a lock, so unlock it first), and `unlock` on an issue that is not locked prints `! Issue <owner>/<repo>#<n> (<title>) is not locked` on standard error and sends nothing. Success prints `Locked as RESOLVED: Issue <owner>/<repo>#<n> (<title>)` (`Unlocked: ...`), as in `gh`. HTTP 403 says that write access to the repository's issues is needed, and any other error shows the server's message. app.copia.io answers `PUT` and `DELETE` on the lock route with HTTP 404; since the issue was just read, the commands then say that the host does not support locking (unlocking) issues, and `docs/parity.md` lists both as Partial. The argument is a number, `#<n>` or an issue URL, as for `issue reopen` (#370)
- `issue pin <number|url>` and `issue unpin <number|url>` pin and unpin an issue with `POST` and `DELETE /repos/{owner}/{repo}/issues/{index}/pin`. The issue is read first: one that is already pinned (or, for `unpin`, not pinned, by its `pin_order`) gets the note `! Issue <owner>/<repo>#<n> (<title>) is already pinned` (`is not pinned`) on standard error and nothing is sent, as in `gh`. HTTP 403 says that write access to the repository's issues is needed, and any other error shows the server's message. app.copia.io answers the pin route with HTTP 404 and sends no `pin_order`; since the issue was just read, the commands then say that the host does not support pinning (unpinning) issues, and `docs/parity.md` lists both as Partial. The argument is a number, `#<n>` or an issue URL, as for `issue reopen` (#369)
- `issue delete <number|url> --yes` deletes an issue with `DELETE /repos/{owner}/{repo}/issues/{index}`. Deletion is irreversible: without `--yes` the command fails with a hint and sends no request, as `repo delete` does; there is no prompt. Gitea lets only repository admins delete an issue, so HTTP 403 says that admin rights are needed, and HTTP 404 reports the issue as not found. app.copia.io refuses the request with HTTP 405; the command then says that the host does not allow deleting issues and points to `issue close`, and `docs/parity.md` lists the command as Partial. The argument is a number, `#<n>` or an issue URL, as for `issue reopen` (#368)
- `issue reopen <number|url>` reopens a closed issue with `PATCH /repos/{owner}/{repo}/issues/{index}` (`state: open`). The issue is read first: one that is already open gets the note `! Issue <owner>/<repo>#<n> (<title>) is already open` on standard error and nothing is sent, as in `gh`. `--comment/-c` posts a comment before the reopen. The argument is a number, `#<n>` or an issue URL; a URL names the repository, and a URL on another host than the active one fails before any request (#367)
- `--limit/-L` (default 30) on `label list`, `org list` and `notification list`; all three page through results, so they no longer stop at the server's first page. `notification list --all` applies to every page (#245)
- `--visibility {public|private}` on `repo list`. The Gitea list endpoints take no visibility filter, so the filter runs on each page and `--limit` counts the kept repositories; paging continues past a page without a match (#172)
- `auth status` prints a `Token:` line for each host, masked with one asterisk per character of the token; `--show-token` prints the full token instead. The config file is not touched (#176)
- `--label/-l` on `search issues` (repeatable or comma separated, sent as `labels=a,b` like `issue list --label`); results come newest first, the issue endpoint takes no sort. `--sort {alpha|created|updated|size|stars|forks}` and `--order {asc|desc}` (default `desc`) on `search repos`; `--order` is ignored without `--sort`, as in `gh search repos`, and an unknown value of either fails before any request (#171)
- `--body/-b` on `pr merge` sets the body of the merge commit (sent as `MergeMessageField`); Gitea keeps its default title and appends the body after a blank line. Combines with `--squash`, `--rebase` and `--delete-branch`; without `--body` the field is left out, so a squash merge keeps its default body (#175)
- `--comments/-c` on `issue view` and `pr view` prints every conversation comment after the body, oldest first, each as `<login> commented <created_at>:` and its text; a second request reads `/issues/{n}/comments`, which also serves pull requests. PR reviews and inline review comments are not shown. `--comments` with `--json` fails before any request; the `issue view` JSON `comments` field stays the count (#173)
- `--assignee/-a` (repeatable) and `--milestone/-m` on `issue create`. `--assignee @me` assigns the authenticated user, read with one `GET /user`. `--milestone` takes a name or a numeric ID and resolves it with `GET /repos/{owner}/{repo}/milestones/{name}`; an unknown milestone fails before the issue is created. `issue edit --milestone` uses the same lookup, so it now takes a name too, and a numeric ID works as before (#169)
- `--add-assignee` and `--remove-assignee` (repeatable) on `issue edit`. Gitea's issue PATCH replaces the whole list, so the current assignees are read with `GET /repos/{owner}/{repo}/issues/{index}` and the changed list is sent; removing a login the issue does not have changes nothing, and removing the last one sends `"assignees": []`. `--assignee` still replaces the list and fails before any request when combined with either new flag. `--remove-label` (repeatable) on `issue edit` resolves names like `--add-label` (repository and organization labels) and sends one `DELETE /repos/{owner}/{repo}/issues/{index}/labels/{id}` per label; an unknown name fails before the issue is changed (#170)
- `--assignee/-a`, `--author/-A`, `--mention`, `--milestone/-m` and `--search/-S` on `issue list`, sent as the server-side filters `assigned_by`, `created_by`, `mentioned_by`, `milestones` (the name as given) and `q` on every page. `@me` in `--assignee` and `--author` stands for the authenticated user, read with one `GET /user` even when both flags use it; without the new flags the request is unchanged (#168)

Assignees (`@me` read with one `GET /user`), label IDs (repository and organization labels, by name) and the milestone ID (name or numeric ID) go into the create body; an unknown label or milestone fails before the pull request is created. If that request fails, the pull request still exists: its URL is printed and the command exits non-zero (#166)
- `--draft/-d`, `--body-file/-F` and `--fill/-f` on `pr create`. Gitea has no draft field, so `--draft` prefixes the title with `WIP: ` unless it already starts with `WIP:` or `[WIP]` (case-insensitive). `--body-file` reads the body from a file, `-` from standard input, and fails with `--body` before any request. `--fill` takes the title and body from `git log --cherry <base>...<head>` (`origin/<base>` when it exists, the head defaulting to the current branch): one commit gives its subject and body, several commits give the branch name and a bulleted list of their subjects, oldest first. An explicit `--title` or `--body` wins, and `--title` is not required with `--fill` (#320)
- `--json` prints only the requested fields: an array of objects for a list, one object for a view. It takes a comma-separated list and can be repeated; an unknown field fails before any request and lists the available fields. Applies to `issue list`, `issue view`, `pr list`, `pr view`, `repo list`, `repo view`, `release list`, `label list`, `org list`, `org view`, `notification list`, `search repos` and `search issues` (#177)

The helpers are `join`, `pluck`, `truncate`, `timeago`, `tablerow` and `tablerender`; the `gh` color helpers are left out. `--template` without `--json`, together with `--jq`, or a template that does not parse fails before any request (#321)
- `--raw-field/-f key=value` on `api` always sends the value as a string; `-f key=value` sends exactly what it sent before (#167)
- `--input <file>` on `api` sends the file as the request body, `-` reads standard input; the default method is then POST and the `Content-Type` stays `application/json` unless `--header` sets another. ### Security

- A host keeps several accounts, as in gh: the config file holds them under `hosts.<host>.users.<login>` (with a `token` only when it is stored in the config file) and the active account under `hosts.<host>.user`, and the commands use the active account's token. A config of an older version (`token` and `user` under the host) is read as one account and written in the new shape on the next save; unknown keys are kept. `auth login` adds the account or updates it and makes it active. `auth logout --user/-u <login>` removes one account and its keyring entry; without `--user` it removes the active one, and the alphabetically first remaining account becomes active (`Switched active account for <host> to <login>`); the last account removes the host. `auth status` lists every account per host, the active one first, with `Active account: true` or `false`. The keyring holds one entry per account (service `copia-cli:<host>`, account = the login). The token order stays `--token` > `COPIA_TOKEN` > the stored token of the active account (#420)
- `auth login` stores the token in the OS keyring (macOS Keychain, Windows Credential Manager, the Secret Service on Linux) under the service `copia-cli:<host>` with the login as the account, and leaves no token in `~/.config/copia/config.yml`, as gh does. Every keyring call gives up after three seconds, so a locked or absent Secret Service cannot hang the command. When the keyring fails, the token goes to the config file in plain text and a warning on standard error names the fallback and the file, never the token; `--insecure-storage` writes the config file on request. The commands read the stored token from the config file first, then from the keyring, so tokens stored by older versions keep working; the next `auth login` on that host moves the token to the keyring. `auth logout` deletes the token from both places, and `auth status` shows where it is stored: `Token: **** (keyring)` or `Token: **** (config file)`, or `Token: none` when neither holds one. The snap has no `password-manager-service` plug and always falls back to the config file. The token order stays `--token` > `COPIA_TOKEN` > the stored token (#19)
- Every save of `~/.config/copia/config.yml` (`auth login`, `auth logout`, `config set`) writes a new file with mode `600` to a temporary file in the same directory and renames it over the old one, so a token is never written into a file other users can read, whatever mode the old file had, and a failed save (a full disk, a crash) leaves the old file as it was. The save refuses a config path that is not a regular file, such as a symlink, with an error that names the path, and an existing file the user cannot write (read-only, or owned by another user). A config directory that group or others can write is set to `700` first; if that fails, the save fails. Before, the file was written in place and a file created with a wider mode kept it (#395)
- Every command follows an HTTP redirect only when it keeps the scheme, host and port of the request, so the `Authorization` header never reaches another server or travels over plain HTTP. A redirect to another origin, including `https://host` to `http://host` or to `https://host:<other port>`, fails the command with an error that names both origins instead of being followed. The 10-redirect limit stays. All commands build their client with `cmdutil.NewHTTPClient()`, the uncalled `api.NewClient` is removed, and a test fails on `&http.Client{}` or `http.DefaultClient` in non-test code under `pkg/` and `internal/` (#333)
- `repo clone` sends the token only to the configured host: an `https` URL whose host equals it (case-insensitive) on the same port, 443 when none is given. Any other URL, such as another host, a look-alike host (`app.copia.io.evil.example`), `http://`, another port or `git@`, is cloned without credentials; before, every `https://` URL got the token. The token is no longer in the clone URL or git's arguments, so other local users cannot read it from the process list: git gets it from a credential helper set through `GIT_CONFIG_*` environment entries under `credential.https://<host>.helper`, which reads it from `COPIA_CLONE_TOKEN`, replaces the user's helpers for that host only, and ignores `store` and `erase`, so no credential store keeps a copy. git asks for credentials per origin, so a redirect from the configured host to another origin does not carry the token; tests pin this with two `git http-backend` servers. A configured host with a wildcard, user name, path, query or fragment is refused, and an invalid `GIT_CONFIG_COUNT` is an error instead of being read as 0; `GIT_CONFIG_*` entries already set are kept. The remote is stored as given, without the post-clone `git remote set-url` (#335)

The filter runs with the command's context and stops when it is canceled (#322)

A script that used `--field n=1` now sends the number `1`; use `--raw-field` or `-f` for the string. - The `--json` field names are the keys the commands print: `user` replaces `author` on `issue view`, `pr list` and `pr view`, and `stars_count` and `forks_count` replace `stars` and `forks` on `repo view`. `html_url` is now listed on `issue view`, `pr view` and `repo view`, and `id` on `release list` and `label list`; these keys were already printed. The `release list` and `repo list` help examples use `tag_name` and `full_name` (#177)
- `.devcontainer/compose.yaml` adds a `dev` service for the Horde sandbox (`horde-dev`): it runs as `1000:100`, keeps the Go caches and `HOME` on named volumes, is limited to 2 GB of memory and ships golangci-lint v2.15.0. bump-go now also updates `.devcontainer/Dockerfile`. The local workflow (`docker-compose*.yml`, `devcontainer.json`, `justfile`) is unchanged (#257)
- All workflows except bump-go read the Go version from `go.mod` instead of a hard-coded `1.26` (#228)
- bump-go opens its pull requests with a GitHub App token, so CI runs on them; its actions are pinned by commit SHA and its `GITHUB_TOKEN` is read-only. Setup and key rotation are in `docs/ci.md` (#238)
- CI measures coverage across packages (`go test -coverpkg=./...`), so code tested from another package counts; unit tests now run every command end to end, `repo clone` and `pr checkout` against a real local git repository, and test coverage is raised to 60% or more (#165)
- `codecov.yml` adds a coverage gate: `codecov/patch` fails when less than 80% of a PR's changed lines are covered. It is not a required check; see `CONTRIBUTING.md` (#255)
- CI uploads coverage to Codecov with GitHub OIDC instead of a token. The upload uses `codecov/codecov-action` v7.1.1 pinned by commit SHA. Tests run through gotestsum, and a second upload sends the JUnit report to Codecov Test Analytics. PRs now also get a `codecov/project` status from the organisation's Codecov configuration: it fails when total coverage drops by more than 1% (#262)
- The unit-test HTTP mock rejects requests that send a token as `?token=` or `?access_token=`; a new integration test checks that Copia refuses them with 403. The docs now state that header auth is the only supported method on Copia since 2026-05-01 (#235)
- The organisation's canonical `close-issues-on-merge.yml` replaces `close-linked-issues.yml`: a PR merged into `develop` closes the issues named in its body's `Closes #N` lines with the comment `Fixed in develop by <sha> (PR #<n>).`; merges into other branches close nothing. The action is pinned by commit SHA and the token defaults to read-only (#264)
- Every workflow sets a read-only `GITHUB_TOKEN` at the top level and widens it per job only where a step needs it; every action is pinned by commit SHA with its tag in a comment (`winget-releaser` moves from `main` to the same commit as `v2`). The scheduled integration test no longer holds `issues: write`: a separate `report-failure` job, which checks out no code, opens the failure issue. The rule is in `CONTRIBUTING.md` (#266)
- bump-go, aur and copr pass secrets, step outputs and `github.ref_name` to their `run:` steps through `env:` and quoted shell variables instead of `${{ }}` in the script. bump-go fails when the version read from go.dev does not match `^[0-9]+\.[0-9]+(\.[0-9]+)?$` (`script/check-go-version.sh`). `go test ./...` fails on a `${{` inside any `run:` block; the rule is in `CONTRIBUTING.md` (#268)
- The workflow expression check also fails on a `${{` in the `script:` input of an `actions/github-script` step, and scans the steps of composite actions under `.github/actions/*/action.yml` (#270)
- Only a repository admin can create a `v*` release tag (new `Release tag creation` ruleset); pushed `v*` tags stay undeletable and immovable for everyone. `docs/releasing.md` and `CONTRIBUTING.md` state the rule (#272)

### Fixed

- `issue create --label` and `issue edit --add-label` resolve names against the organization labels as well as the repository labels, so org-level labels can be attached; a repository label wins on a name clash. `issue create` now sends label IDs instead of raw names (#216)
- `issue edit --add-label` looks up label names on every page of the repository labels, so labels past the first 50 resolve instead of failing with "not found" (#246)
- `issue list` pages through results, so `--limit` above 50 returns up to that many issues instead of stopping at the first page; `--state` and `--label` apply to every page (#215)
- `pr list`, `repo list` (user and `--org`), `release list`, `search issues` and `search repos` page through results the same way, so `--limit` above 50 returns up to that many items; filters and the search query apply to every page (#244)
- Linux install guide now points Fedora/RHEL users to the `cbiro/copia-cli` COPR project; `qubernetic/copia-cli` does not exist (#233)
